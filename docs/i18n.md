# Languages

The public site is served in English and Danish. English is the default: every
record's ordinary fields hold the English text, and Danish is stored as a
translation on top of it. Anything not translated yet falls back to English,
field by field, so a half-translated site still works.

The CMS itself stays in English.

## URLs

Every public page lives under a locale prefix:

```
/en/blog/hello-world
/da/blog/hello-world
```

Slugs are shared by both languages, so switching language keeps you on the same
page. `web/proxy.ts` handles everything without a prefix:

| Request | Result |
| --- | --- |
| `/da/...`, `/en/...` | Served. The proxy sets the `x-site-locale` request header (for `<html lang>`) and remembers the choice in the `locale` cookie. |
| `/`, `/blog/x`, any other unprefixed path | 307 to the same path under a locale: the `locale` cookie if set, else the best match in `Accept-Language`, else English. Query strings are kept. |
| `/admin/...`, `/api/...` | Untouched. No locale. |
| Any path with a dot (`/feed.xml`, `/sitemap.xml`, `/robots.txt`, `public/` files) | Untouched. |

`/feed.xml` is still the English feed, so subscriptions made before this
change keep working. `/en/feed.xml` and `/da/feed.xml` are the per-language
feeds.

Each page emits `hreflang` alternates and a canonical URL
(`alternatesFor()` in `web/lib/i18n/server.ts`), and the sitemap lists every
page once per locale with its siblings, so search engines treat the two
versions as translations rather than duplicates.

## Where the text lives

**Site chrome** (nav, headings, buttons, dates, empty states) is in
`web/lib/i18n/dictionaries.ts`. `en` defines the shape and `da` is typed against
it, so a missing Danish string fails `npm run typecheck`. Placeholders such as
`{n}` are filled with `format()`. Values are plain strings so a slice of the
dictionary can be handed to a client component as props (see `ProjectDemo`).

**Content** is in the database:

| Record | Translatable | Shared by both languages |
| --- | --- | --- |
| posts | title, summary, body | slug, tags, cover, status, dates |
| projects | title, tagline, case study | slug, tech, URLs, demo, media, ordering |
| cv entries | title, organization, location, description, highlights | kind, dates, ordering |
| settings `site` | headline, description, location | name, email |
| settings `about` | heading, body | avatar |
| settings `socials` | nothing | the links |

Posts, projects and CV entries each have a `translations` JSONB column
(migration `0002_translations.sql`), keyed by locale:

```json
{"da": {"title": "Hej, verden", "summary": "", "body_markdown": "..."}}
```

Settings blobs carry the same shape inside their own JSON value, under a
`translations` key. Only top-level string fields are overlaid.

## How a public read is localized

Every public endpoint takes `?lang=en|da` (missing means `en`, anything else is
a 400). The store does the overlay, in `api/internal/store/i18n.go`, for the
same reason it does draft filtering: a new endpoint built on the store cannot
forget it.

- A non-empty Danish field replaces the English one. An empty one falls back.
- CV highlights fall back as a whole list, not bullet by bullet.
- A post's reading time is recomputed from the Danish body when there is one.
- `translations` is removed from the response.
- Posts and projects get a `locale` field saying which language the body was
  actually served in. When it differs from the page's locale, the page shows a
  short "not translated yet" note and marks the body `lang="en"`.

Admin endpoints return records raw, `translations` included, so the CMS can edit
both languages. A PUT replaces the whole `translations` map; leaving it out
clears it.

Search (`?q=`) matches the English fields and the translations.

## Caching

Cache tags stay per content type (`posts`, `projects`, `cv`, `settings`), not per
locale. One CMS save changes both languages at once, so it has to purge both.

## Adding a third language

1. **Go**: add the constant to `models.Locale`, to `Valid()`, and to the error
   messages in `httpapi/i18n.go`.
2. **Types**: add it to `Locale` in `web/lib/api/types.ts`.
3. **Config**: add it to `LOCALES`, `INTL_LOCALE` and `OG_LOCALE` in
   `web/lib/i18n/config.ts`.
4. **Dictionary**: add a full dictionary in `dictionaries.ts`. The type checker
   lists every missing string.
5. **Header**: the language switch in `components/site-header.tsx` assumes two
   locales and links to "the other one". Turn it into a list.
6. **CMS**: add a name to `NAMES` in `components/admin/locale-tabs.tsx`, and a
   `filled` entry wherever `LocaleTabs` is used.

No migration is needed: the `translations` columns are already keyed by locale.
